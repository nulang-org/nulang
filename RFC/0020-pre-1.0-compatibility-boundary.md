# RFC 0020: Pre-1.0 Compatibility Boundary

- **Status:** Draft
- **Tier:** Governance / compatibility policy
- **Language-version at effect:** none until accepted and implemented
- **Supersedes:** RFC 0001 and RFC 0002 only where they imply an irrevocable compatibility promise before Nulang reaches a production-stable release
- **Depends on:** RFC 0001, RFC 0002, RFC 0010

## Summary

Nulang currently labels several surfaces as **Frozen** while the implementation is still alpha, has no established external compatibility corpus, and is actively closing runtime-soundness, authority, ownership, durability, and migration invariants.

This RFC keeps the project's long-term compatibility goal but separates two concepts that are currently conflated:

1. **versioned compatibility targets** used during the pre-1.0 stabilization period; and
2. **irrevocable post-1.0 compatibility guarantees** made only after the implementation and conformance evidence are strong enough to support them.

The goal is not to make breaking changes easy. The goal is to avoid permanently binding Nulang to an unsound or insufficiently proven representation merely because it was named `v1` early in the project.

## Motivation

Nulang's durability thesis depends on compatibility guarantees being credible. A promise that is stronger than the evidence behind it weakens that thesis rather than strengthening it.

Today the project simultaneously states that:

- the implementation is alpha and breaking changes should be expected before v1.0;
- `.nbc` format v1, NUL0 v1, the value layout, Nulang Core, and several effects are Frozen forever;
- core runtime and semantic invariants are still being hardened under the P0 stabilization gate.

Those statements can be reconciled by treating current Frozen surfaces as **provisional compatibility contracts** during pre-1.0 development, with changes requiring an RFC, explicit version bump, migration/conversion tooling where applicable, and conformance evidence.

## Proposed policy

### 1. Pre-1.0 Frozen means "change only through an explicit compatibility event"

Before the first production-stable Nulang release, a Frozen surface MUST NOT change silently or in-place.

A breaking change requires all of the following:

1. an accepted RFC explaining why the existing contract is unsafe, incomplete, or materially blocks the language's goals;
2. a new language, wire, artifact, or layout version as appropriate;
3. fail-closed version negotiation or rejection;
4. a migration, converter, compatibility reader, or explicit documented incompatibility boundary where technically possible;
5. conformance tests for both the old and new behavior during the supported transition window;
6. release-note and tooling guidance for affected users.

This preserves the practical discipline of Frozen without pretending that an alpha representation is already an eternal ABI.

### 2. No in-place reinterpretation

The following remains prohibited even before 1.0:

- changing the meaning of existing `.nbc` bytes without a format-version change;
- changing NUL0 message semantics without protocol negotiation/versioning;
- reinterpreting serialized values or durable actor state under the same schema/semantic identity;
- silently widening authority/capability semantics;
- activating incompatible durable state under newer code without a proven migration path.

A pre-1.0 compatibility event creates a **new versioned contract**; it does not mutate history.

### 3. Post-1.0 Frozen regains the strong meaning

After the stability exit criteria below are satisfied and the project ratifies a production-stable language release, Frozen once again means the strong current governance definition:

> a Frozen surface does not break within the major compatibility line; incompatible evolution requires a new major language/protocol/format generation and a migration path.

The project should not claim stronger guarantees than this across all future major generations. A "100-year language" should preserve the ability to read, migrate, or faithfully execute old artifacts, not prohibit every future major-version improvement.

## Stability exit criteria

The maintainer SHOULD NOT ratify the first production-stable compatibility generation until all of the following hold:

1. **Runtime soundness:** the P0 raw `Value`/pointer provenance and ownership invariants are integrated and exact-head validated.
2. **Authority closure:** source capability grants flow through compiler metadata, exact spawn provenance, delegation, recovery/migration, and host-boundary enforcement without fail-open paths.
3. **Durability upgrades:** durable actor/entity state has canonical semantic/schema identity and deterministic versioned migration behavior, including fail-closed recovery on incompatibility.
4. **Backend contract:** bytecode remains the semantic oracle and the canonical portable/cloud WASM target passes differential/conformance tests for the supported production surface.
5. **Wire/artifact corpus:** at least two released compiler/runtime versions can read or explicitly migrate the previous generation's supported artifacts and protocol fixtures.
6. **Cloud golden path:** Nulang Cloud demonstrates `Nulang package -> canonical WASM -> isolated deploy -> durable actor -> hard crash/restart recovery -> continued execution` using released artifacts rather than test-only shims.
7. **External compatibility evidence:** at least one non-trivial application outside the compiler/runtime test suite survives an upgrade across released Nulang versions without source or durable-state ambiguity.

These are evidence requirements, not calendar requirements.

## Surface classification during pre-1.0

The existing tier names remain useful. Their interpretation becomes:

- **Frozen (pre-1.0):** versioned compatibility target; breaking evolution only through the process in this RFC.
- **Stable:** source/semantic contract requiring RFC + deprecation/migration discipline.
- **Experimental:** no compatibility promise beyond explicit artifact/protocol version rejection.

No current surface is automatically downgraded to Experimental by this RFC.

## Relationship to semantic identity and durable migration

This RFC intentionally reinforces the semantic-identity work rather than weakening it.

A durable activation should prove one of:

1. persisted semantic/schema identity is compatible with the target artifact;
2. an explicit deterministic migration chain exists and succeeds transactionally; or
3. activation fails closed while preserving the last valid state.

Compatibility policy should be enforced by machine-readable identities and conformance fixtures wherever possible, not by documentation alone.

## Relationship to Nulang Cloud

Nulang Cloud MUST consume Nulang's versioned semantic/runtime contract rather than defining a second language semantics layer.

Cloud may implement host effects, isolation, placement, persistence infrastructure, metering, billing, deployment, and observability, but it should not independently redefine:

- effect meaning;
- capability semantics;
- actor/message semantics;
- semantic identity;
- durable state compatibility;
- artifact language versioning.

Those remain Nulang-owned contracts exposed to Cloud through versioned artifacts/protocols/WIT interfaces.

## Non-goals

This RFC does not:

- authorize gratuitous syntax churn;
- weaken fail-closed compatibility checks;
- reset existing format or protocol version numbers;
- require a breaking change to any current surface;
- change runtime behavior by itself;
- declare any currently experimental subsystem production-stable.

## Alternatives considered

### Keep the current wording unchanged

This maximizes apparent stability today but creates a risk that an alpha implementation detail becomes a permanent architectural constraint before meaningful compatibility evidence exists.

### Remove Frozen entirely until 1.0

This is too weak. Nulang benefits from strict versioning discipline now, particularly for bytecode, durable state, and wire protocols.

### Freeze everything and introduce v2 whenever needed

This is mechanically workable, but calling every pre-user correction a new eternal major generation creates compatibility archaeology without providing real user value. The policy above keeps version bumps mandatory while reserving the strongest permanence claim for a proven stable generation.

## Implementation plan if accepted

1. Update `GOVERNANCE.md` to define the pre-1.0 interpretation of Frozen.
2. Update README/SPEC wording so `1.0-frozen` is not confused with a production-stable 1.0 release.
3. Add explicit version-negotiation/conformance fixtures for `.nbc`, NUL0, value-layout serialization boundaries, and durable state identities.
4. Make the P0 stabilization gate and durable migration work explicit prerequisites for production-stable ratification.
5. Record the policy change in `CHANGELOG.md` as governance/compatibility clarification, not a runtime behavior change.

## Resolution

Draft. Requires maintainer review and explicit acceptance before changing the existing governance contract.
